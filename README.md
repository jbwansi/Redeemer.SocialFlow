# Redeemer SocialFlow

The Clean Architecture solution is `Redeemer.SocialFlow.slnx`. Its runnable host is
`Redeemer.SocialFlow.Api`; the older `Redeemer.SocialFlow` web template is outside the solution.

## Local persistence

The API reads `ConnectionStrings:SocialFlow` from its `appsettings.json`, defaulting to
`Data Source=socialflow.db`. Relative SQLite paths resolve against the process working
directory. Override with `ConnectionStrings__SocialFlow` for another location.
Local database files are ignored by Git.

From the solution directory, with the .NET 10 SDK and `dotnet-ef` 10.0 installed:

```powershell
dotnet ef database update --project Redeemer.SocialFlow.Infrastructure --startup-project Redeemer.SocialFlow.Api
dotnet run --project Redeemer.SocialFlow.Api
```

Schema changes are applied explicitly with migrations, not automatically at API startup.
The initial migration creates `SocialPosts` and EF's migration history table.

Infrastructure owns the SQLite provider, `SocialFlowDbContext`, Fluent API mappings,
and migrations. Application uses `ISocialFlowDbContext` (EF Core's provider-independent
`DbSet` and `SaveChangesAsync`) without referencing Infrastructure. Both context types
resolve to the same scoped instance. No repository layer is needed.

Domain has no EF dependency. A private parameterless constructor initializes the system
clock when posts are loaded; public creation and transitions still use the domain rules.
IDs are generated by the domain. No arbitrary string length limits are added.
DateTimeOffset values are stored as SQLite TEXT, preserving offsets and tick precision.
SQLite does not support server-side ordering or range comparisons on DateTimeOffset.

## Application use cases

`AddApplication()` registers the scoped `ISocialPostService`. It exposes create, get,
list, update, delete, submit for review, approve, reject, schedule, and cancel operations
using immutable requests and `SocialPostDto` results. Entities are kept inside the use
case implementation. Reads use DTO projection without tracking. Mutations invoke domain
methods and save through `ISocialFlowDbContext`, forwarding the caller's cancellation token.
`SocialPost.EnsureCanDelete()` owns the draft/rejected deletion rule.

Get returns null for a missing ID; mutations throw `PostNotFoundException` with that ID.
Domain validation exceptions propagate unchanged. Update replaces editable fields;
null optional values clear those fields. Schedule accepts a `DateTimeOffset` instant.

List filters combine with AND: optional platform, status, and inclusive `CreatedFrom` /
`CreatedTo` bounds on **CreatedAt**. Reversed bounds throw `ArgumentException`. Results
sort by CreatedAt descending, then ID ascending. SQLite applies platform/status filters;
the application streams DTOs and compares dates as instants in memory to preserve
offsets and tick precision. Listing is unpaginated and reads every row matching the SQL
filters, so larger datasets will need a queryable UTC storage strategy and pagination.

## REST API

The thin `PostsController` delegates to `ISocialPostService` and passes request cancellation
tokens. JSON requests and responses use the Application records; no EF access or workflow
rules are implemented in the controller. JSON enum values use their existing numeric values;
query filters accept enum names or numbers.

| Method | Path | Success |
| --- | --- | --- |
| POST | `/api/posts` | 201, post DTO and Location header |
| GET | `/api/posts/{id}` | 200, post DTO |
| GET | `/api/posts` | 200, DTO array |
| PUT | `/api/posts/{id}` | 200, updated DTO |
| DELETE | `/api/posts/{id}` | 204, empty body |
| POST | `/api/posts/{id}/submit-for-review` | 200, updated DTO |
| POST | `/api/posts/{id}/approve` | 200, updated DTO |
| POST | `/api/posts/{id}/reject` | 200, updated DTO |
| POST | `/api/posts/{id}/schedule` | 200, updated DTO |
| POST | `/api/posts/{id}/cancel` | 200, updated DTO |

List query parameters are `platform`, `status`, `createdFrom`, and `createdTo`, with the
semantics described above. Encode date offsets in URLs (for example, `+02:00` becomes
`%2B02:00`). Create accepts `title`, `content`, and `platform`; update accepts `title`,
`content`, `callToAction`, `visualBrief`, and `visualUrl`. Schedule accepts
`{"scheduledAt":"2027-01-01T12:00:00Z"}`. Other workflow actions need no request body.

Errors use `application/problem+json`, with status, title, type, instance, and traceId:

- Missing posts: 404 for both reads and mutations.
- Domain validation and invalid workflow transitions: 400 with the domain message.
- Malformed JSON, route/query binding errors, and invalid date ranges: 400. Binding
  failures also include the standard validation errors dictionary.
- Unexpected exceptions: 500 with a generic message in every environment; exception
  details are logged server-side with the trace ID.
- Unmatched routes and unsupported methods/media types also use ProblemDetails.

No schema initialization happens on API startup; apply migrations as described above.

### Development documentation

Run `dotnet run --project Redeemer.SocialFlow.Api -- --environment Development`.
At the host address printed by the command, open `/scalar/v1` for interactive Scalar
documentation or `/openapi/v1.json` for the generated OpenAPI document. Both routes are
mapped only in Development. The document includes request/response schemas, operation
summaries, filter parameters, and success/error status codes.

Uses Microsoft.AspNetCore.OpenApi 10.0.12 and Scalar.AspNetCore 2.17.8 following the
[Scalar ASP.NET Core integration](https://github.com/scalar/scalar/blob/main/documentation/integrations/aspnetcore/integration.md).

## Verification

The React + TypeScript frontend lives in `Redeemer.SocialFlow.Web`. It includes the
Dashboard, Editorial Calendar, and Posts workspace with create/edit and workflow
actions. See [frontend setup and validation](Redeemer.SocialFlow.Web/README.md) for
the Vite API proxy, local commands, deployment configuration, and frontend tests.

```powershell
dotnet build Redeemer.SocialFlow.slnx
dotnet test Redeemer.SocialFlow.slnx --no-build
```

Integration tests start the API host with isolated temporary SQLite files, apply the
actual migrations, and use separate scopes to verify persisted data and domain behavior.
Files are removed after each test.
